# FutureverseAI RAG Pipeline

Technical documentation for the FutureverseAI retrieval-augmented generation (RAG) pipeline — a UPSC (Indian civil-service exam) study assistant built on a fork of **Open WebUI** with a **knowledge-graph layer** powered by **AutoSchemaKG / `atlas_rag`**.

> Scope: this document covers the RAG/KG subsystem (ingestion, retrieval, generation, stores, ops). For general Open WebUI features (chat, auth, models), see the upstream documentation.

---

## 1. Overview

The pipeline combines three retrieval signals and fuses them at query time:

| Signal | Store | Purpose |
|---|---|---|
| **Dense vectors** | Weaviate (HNSW) | Semantic similarity over contextually-enriched chunks |
| **Sparse keywords** | Weaviate (native BM25) | Exact entity/term matching |
| **Knowledge graph** | Neo4j | Entity relationships, causal/structural reasoning, citations |

Generation runs through an Ollama-hosted LLM with a UPSC-tuned prompt that enforces inline `[id]` source citations.

**Tech stack:** FastAPI · SvelteKit (Svelte 5) · Weaviate · Neo4j · MySQL · Redis · Ollama · sentence-transformers / bge-m3 · LangChain.

## 2. Architecture

```mermaid
flowchart TB
    subgraph Ingestion["📥 Ingestion (routers/retrieval.py, knowledge.py)"]
        U[Upload file / text / URL] --> L[Loaders<br/>marker · mineru · mistral · tavily · youtube]
        L --> RP["run_ingestion_pipeline (pipeline_agents.py)"]
        RP --> CK[ChunkingAgent<br/>hierarchical parent→child]
        CK --> KW[KeywordAgent<br/>regex / KeyBERT / llama3]
        KW --> CE[ContextualEnrichmentAgent<br/>contextual_chunking.py]
        CE --> DD[ChunkDeduplicationAgent]
        DD --> EM[EmbeddingAgent]
        EM --> SD[SemanticDeduplicationAgent]
        SD --> IX[IndexingAgent → Weaviate]
        RP -. parallel .-> EX["extract_and_store (extractor.py)"]
        EX --> KG[(Neo4j KG)]
        EX -. background .-> SP[semantic_promoter<br/>typed edges]
        EX -. every 50 .-> CD[community_detection<br/>Leiden]
    end

    subgraph Query["🔎 Query (utils.get_sources_from_items)"]
        Q[User question] --> QE[Query expansion<br/>multi-query]
        QE --> HS["query_doc_with_hybrid_search"]
        HS --> BM[Weaviate BM25]
        HS --> VS[Weaviate vector]
        BM --> EN[Ensemble RRF]
        VS --> EN
        EN --> RR[Cross-encoder rerank<br/>+ parent dedup]
        QE --> GS["get_graph_source (graph_rag.py)"]
        GS --> KG
        RR --> MERGE[Merge + graph-guided re-rank]
        GS --> MERGE
        MERGE --> GEN[LLM answer + [id] citations]
    end

    IX --> VDB[(Weaviate)]
    VDB --> VS
    KG --> GS
```

**Two independent ingestion paths** run from a file upload: the **vector path** (`run_ingestion_pipeline` → Weaviate) and the **KG path** (`extract_and_store` → Neo4j, via `atlas_rag` with an Ollama fallback extractor). At query time, vector + BM25 results are reranked, then **knowledge-graph context is injected** and used to re-rank vector chunks that mention graph entities.

## 3. Components

### Ingestion — `retrieval/pipeline_agents.py`
An **agent + checker** pipeline; each stage validates its output before the next runs:

1. **ChunkingAgent** — markdown-header pre-split, then hierarchical parent→child chunking (`CHUNK_SIZE` parent, `CHUNK_SIZE//4` child) with multi-granularity metadata (`parent_id`, `chunk_id`, sibling/child links, breadcrumb).
2. **KeywordAgent** — per-chunk keywords for BM25 (`regex` | `keybert` | `llama3`).
3. **ContextualEnrichmentAgent** (`contextual_chunking.py`) — prepends a `[CONTEXT]` block (document/chapter/section/topic) generated by a local LLM; has retries, a circuit breaker, and a fallback counter.
4. **ChunkDeduplicationAgent** — SHA-256 exact dedup by `file_id` then file hash (fail-open).
5. **EmbeddingAgent** — dense vectors via the configured engine.
6. **SemanticDeduplicationAgent** — near-duplicate drop by cosine similarity (off by default).
7. **IndexingAgent** — Weaviate dual-index insert (HNSW + inverted), with post-insert verification.

### Knowledge graph — `retrieval/graph/`
- **`extractor.py`** — runs `atlas_rag` KG construction per document, imports CSVs to Neo4j (**UNWIND-batched**), with a direct-Ollama fallback extractor. Owns the pooled Neo4j driver and `run_query` (with retry + query timeout).
- **`semantic_promoter.py`** — promotes free-text `RELATES_TO` edges into typed semantic edges (`CAUSES`, `GOVERNED_BY`, `TESTED_IN`, …) in **batched UNWIND** passes.
- **`community_detection.py`** — Leiden community detection (igraph + leidenalg), batched writes.
- **`graph_rag.py`** — `get_graph_source()`: keyword/alias expansion → multi-signal Neo4j search (entities, relations, concepts, topics, communities, paths) → LLM context block + entity anchors for re-ranking.

### Retrieval — `retrieval/utils.py`
- **`query_doc_with_hybrid_search`** — Weaviate BM25 + vector **EnsembleRetriever** with dynamic weighting, **cross-encoder reranking** (`RerankCompressor`), pre-rerank dedup, and parent-chunk dedup.
- **`get_sources_from_items`** — orchestrates per-collection hybrid search, **injects KG context**, and applies **graph-guided re-ranking** (boosts chunks mentioning graph entities). Offloaded via `asyncio.to_thread`.
- **`get_embedding_function`** — engines: `""`/`sentence_transformers` (preloaded model), `ollama`, `openai`, `azure_openai`, and opt-in `sentence_transformers_cuda` (dedicated CUDA stream).

### Stores
- **Weaviate** — vectors + BM25 (`VECTOR_DB=weaviate`).
- **Neo4j** — knowledge graph.
- **MySQL** — application data (`DATABASE_URL`).
- **Redis** — sessions / pub-sub (and recommended RAG caching — see §8).

## 4. Setup & installation

### Prerequisites
- Python **3.11**, Node **22**
- Running **Weaviate**, **Neo4j 5.x**, **MySQL 8**, **Redis 7**, **Ollama** (with the configured models pulled)
- NVIDIA GPU + CUDA 12.8 for the pinned `torch==2.11.0+cu128` build (CPU works with the slim/CPU install path)

### Install
```bash
# Backend
cd backend
pip install -r requirements.txt -r requirements-dev.txt   # dev tools split out (Phase 2)
# Frontend
cd ..
npm ci && npm run build
```

### Configure
```bash
cp backend/.env.example backend/.env
# Edit backend/.env — see §5. The feature flags that enable hybrid search,
# reranking and the KG are documented at the bottom of .env.example.
```

### Run
```bash
# Option A — full stack via Docker (recommended)
docker compose -f docker-compose.prod.yaml up -d --build

# Option B — backend directly
cd backend && bash start.sh          # Linux/macOS
#            or start-backend.ps1     # Windows
```

`docker-compose.prod.yaml` defines the complete stack (backend + Weaviate + Neo4j + MySQL + Redis + Ollama) with health checks, dependency ordering, GPU reservations, and Docker secrets.

## 7. Operations

- **Health checks** — `/health` (liveness), `/health/db` (DB). Dockerfile `HEALTHCHECK` polls `/health`.
- **Logging** — `loguru`; control with `GLOBAL_LOG_LEVEL` / `LOG_LEVEL`. (Pipeline progress currently uses `print()`; migrating to structured logs is recommended.)
- **Tracing/metrics** — OpenTelemetry is instrumented (`utils/telemetry/`: FastAPI, httpx, Redis, SQLAlchemy, logging). Point the OTLP exporter at your collector. Useful RAG metrics to add: retrieval/rerank latency, embedding-cache hit rate, KG query time, ingestion throughput, contextual-chunking `FALLBACK_COUNTER`.
- **Background maintenance** (triggered from KG ingestion in `extractor.py`):
  - after every import → `semantic_promoter` (typed-edge promotion)
  - every 25 imports → edge dedup + global UPSC promotion
  - every 50 imports → community detection
- **Scaling** — `WEBUI_SECRET_KEY` **must be a shared, stable, CSPRNG-generated value** across replicas (do not auto-generate per container) or JWTs break across instances.

## 8. Caching (recommended)

Currently only an **intra-request** embedding cache exists (unique queries embedded once per request). Recommended additions (Redis is already a dependency):
1. **Query-embedding cache** — key `sha256(model + dim + normalized_query)`, TTL ~24h.
2. **Result cache** — for identical `(query, kb_id, top_k)`, short TTL.
3. **Reranker score cache** — key `(query_hash, chunk_hash)`.

Include the embedding model + dimension in cache keys so a model change auto-invalidates.

## 9. Versioning

Adopt **SemVer for the pipeline, decoupled from the upstream Open WebUI version**:
- **MAJOR** — embedding model/dimension change, Neo4j KG schema change, vector schema change, or public API break (any of these requires operator action, e.g. re-indexing).
- **MINOR** — backward-compatible features (new retrieval strategy, loader, endpoint, edge type).
- **PATCH** — bug fixes, dependency bumps, perf with no schema/API/index impact.

Track `EMBEDDING_MODEL` + `EMBEDDING_DIM`, `KG_SCHEMA_VERSION`, and `VECTOR_SCHEMA_VERSION` as explicit constants stamped into stored metadata, and assert them on startup.

## 10. Known limitations & follow-ups

Items identified during the audit that are documented rather than fully resolved:

- **Query-time KG fan-out** (`graph_rag.get_graph_source`) issues many Neo4j round-trips per question; batching the per-keyword fulltext queries into `CALL {}` subqueries is recommended but needs live-Neo4j validation.
- **Cross-request caching** is not yet implemented (see §8).
- **Strict grounding** — the default RAG template permits answering from model knowledge when context is missing; add a `RAG_STRICT_GROUNDING` toggle for closed-book behavior.
- **Chunking** is character-based with small children; token-based sizing + trimming embedded boilerplate is recommended (validate with a recall@k eval set using `atlas_rag/evaluation`).
- **Dockerfile** runs as root by default (set a non-root UID/GID) and its `torch<=2.9.1` pin conflicts with `requirements.txt` (`torch==2.11.0+cu128`) — reconcile before release.
- **Devanagari content** is stripped by the cp1252 sanitizer in KG extraction — move to UTF-8 end-to-end.
