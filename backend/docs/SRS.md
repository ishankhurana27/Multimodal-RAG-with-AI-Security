# 1. Introduction

## 1.1 Purpose

This document specifies the software requirements for **FutureVerse AI**, a
Retrieval-Augmented Generation (RAG) platform purpose-built for **UPSC civil
services exam preparation**. The platform ingests an authoritative study corpus
(primarily the **NCERT** textbook set), chunks and indexes it, and answers
learner questions with grounded, citable responses generated by a Large Language
Model (LLM).

The SRS defines the functional and non-functional requirements, external
interfaces, data model, and architecture of the system for the **v1** release.
It is the reference contract between stakeholders (product, engineering,
academic) and the implementation.

## 1.2 Document Conventions

- **FR-n** — Functional Requirement.
- **NFR-n** — Non-Functional Requirement.
- Priority: **H** (high / must-have), **M** (medium / should-have), **L** (low /
  could-have).
- Monospace denotes code identifiers, config keys, table names, or model names.

## 1.4 Product Scope

FutureVerse AI is a web application derived from an open-source conversational-AI
base (Open WebUI lineage, rebranded `futureverse_ai`) and specialised for exam
preparation. In scope for v1:

- Corpus ingestion (PDF / MD / TXT / DOCX) with two selectable chunking
  strategies (**Hierarchical + Contextual** and **Foundation / paragraph-level**).
- Hybrid retrieval (keyword + vector) with cross-encoder re-ranking.
- Conversational RAG chat with source-grounded answers.
- Knowledge-base and document management.
- Role-based user management, authentication, and audit logging.
- Model management via a local LLM runtime (Ollama).
- Admin configuration of RAG, chunking, embedding, and retrieval parameters.

**Out of scope for v1:** mobile-native apps, payment/subscription billing,
automated question-paper generation, and the LLM attribute-tagging (Q-matrix)
pipeline (built but deferred — see §8.2).

## 1.5 Definitions, Acronyms, and Abbreviations

| Term | Meaning |
|---|---|
| RAG | Retrieval-Augmented Generation |
| Chunk | A retrievable text unit derived from a source document |
| Parent / child chunk | Small searched unit (child) that expands to a larger served unit (parent) |
| Foundation chunking | Paragraph-level, verbatim, content-type-aware strategy |
| Hierarchical chunking | Fixed-size parent/child strategy with contextual enrichment |
| BM25 | Keyword ranking function used for lexical search |
| Embedding | Dense vector representation of text for semantic search |
| RRF | Reciprocal Rank Fusion (merges lexical + vector results) |
| Reranker | Cross-encoder that re-scores candidate chunks against a query |
| Weaviate | Vector database (HNSW index + BM25) |
| Ollama | Local LLM runtime serving `qwen2.5:7b`, `llama3`, etc. |
| Q-matrix / AKU | Attribute/knowledge-unit vocabulary (deferred tagging input) |
| RBAC | Role-Based Access Control |
| NCERT | National Council of Educational Research and Training (source corpus) |

# 2. Overall Description

## 2.1 Product Perspective

FutureVerse AI is a **self-hosted, multi-tier web application**. It builds on a
mature conversational-AI front end and back end, and adds a domain-specialised
**ingestion and retrieval pipeline** plus **exam-prep-oriented content
management**. It integrates several storage engines, each with a distinct role:

| Store | Role |
|---|---|
| **MySQL** (`futureverserag`) | System of record: users, auth, chats, files, knowledge bases, config |
| **Weaviate** | Vector + BM25 index of corpus chunks |
| **Neo4j** | Knowledge graph over corpus concepts (graph-augmented retrieval) |
| **MongoDB** | Q-matrix / AKU attribute vocabulary (for deferred tagging) |
| **Ollama** | Local LLM inference and enrichment |

## 2.2 Product Features (Summary)

1. Authentication, user, group, and role management.
2. Knowledge-base and document management.
3. Corpus ingestion pipeline (chunk → enrich → embed → index) with agent/checker
   validation.
4. Selectable chunking strategy (Foundation / Hierarchical).
5. Hybrid retrieval + re-ranking.
6. Conversational RAG chat with citations.
7. Model management (local LLMs).
8. Admin settings for RAG/chunking/embedding/retrieval.
9. Prompts, tools, functions, notes, and memory.
10. Collaboration (channels) and feedback.
11. Audit logging.

## 2.3 User Classes and Characteristics

| User class | Description | Key privileges |
|---|---|---|
| **Learner / Student** | Primary end user preparing for UPSC | Chat, browse knowledge, give feedback |
| **Academic Content Lead** | Curates corpus and validates content quality | Upload/curate knowledge, review chunks |
| **Administrator** | Configures the platform | Full settings, user/model management |
| **System / Service account** | Automated jobs (ingestion workers) | Pipeline execution, indexing |

## 2.4 Operating Environment

- **Server OS:** Windows 11 / Linux (dev on Windows 11; production Linux-capable).
- **Runtime:** Python 3.11 (FastAPI backend); Node.js (SvelteKit build).
- **Containers:** Docker Desktop / Docker Engine (Weaviate, optional Neo4j).
- **Databases:** MySQL 8.x, Weaviate 1.27.x, Neo4j 5.x, MongoDB 6.x.
- **LLM runtime:** Ollama with `qwen2.5:7b` (enrichment) and chat models.
- **GPU:** Optional but recommended for embedding + reranking throughput.
- **Client:** Modern desktop/tablet browser (Chrome, Edge, Firefox, Safari).

## 2.5 Design and Implementation Constraints

- Back end is **FastAPI**; front end is **SvelteKit** (Open WebUI lineage).
- Configuration follows a **PersistentConfig** model: values in the `config` DB
  table override `.env` at runtime.
- Corpus text integrity: Foundation mode must store **verbatim** chunk text (no
  `[CONTEXT]` enrichment) to preserve citation fidelity.
- All LLM usage is **local (Ollama)**; no external LLM API dependency required.
- Embedding dimension is fixed per collection (**1024**, `bge-large-en-v1.5`);
  changing the embedding model requires re-ingestion.
- Weaviate query calls that fetch a file's chunks must set an explicit high
  `limit` (default page size 25 truncates large files).

## 2.6 Assumptions and Dependencies

- MySQL is reachable and the service user is granted for the connecting host
  (see §8.3 operational note).
- Docker is running before ingestion/retrieval (Weaviate dependency).
- Ollama is installed with required models pulled locally.
- The NCERT corpus is licensed/available for ingestion.
- Q-matrix vocabulary (MongoDB) is a prerequisite for the deferred tagging phase.

## 3.3 Corpus Ingestion Pipeline

**Priority: H**

A staged, agent-driven pipeline: **chunk → keyword → contextual-enrich → dedup →
embed → index**, with a checker validating each stage before advancing.

| ID | Requirement | Pri |
|---|---|---|
| FR-3.1 | The pipeline shall extract text via the configured extraction engine (Marker/Docling/PyPDF/Tika). | H |
| FR-3.2 | The pipeline shall chunk text using the configured strategy (§3.5). | H |
| FR-3.3 | The pipeline shall extract BM25 keywords per chunk (regex / KeyBERT / llama3). | M |
| FR-3.4 | In Hierarchical mode, the pipeline shall prepend an LLM `[CONTEXT]` block before embedding. | M |
| FR-3.5 | In Foundation mode, the pipeline shall store verbatim text and skip `[CONTEXT]` enrichment. | H |
| FR-3.6 | The pipeline shall embed each chunk (`bge-large-en-v1.5`, 1024-dim). | H |
| FR-3.7 | The pipeline shall index chunks + metadata into Weaviate (HNSW + BM25). | H |
| FR-3.8 | Each stage shall be validated by a checker; a failed checker shall abort ingestion. | H |
| FR-3.9 | The pipeline shall preserve `file_id` on every chunk for filtering and deletion. | H |
| FR-3.10 | Re-ingestion shall purge and rebuild a document's collection (`overwrite=True`). | M |

## 3.4 Chunking Strategy Selection

**Priority: H**

| ID | Requirement | Pri |
|---|---|---|
| FR-4.1 | Admins shall select the chunking strategy in Admin → Settings → Documents. | H |
| FR-4.2 | The system shall support **Hierarchical** (parent 1000 / child 250 chars, contextual enrichment). | H |
| FR-4.3 | The system shall support **Foundation** (paragraph-level, 2–6 sentences, verbatim, content-type-aware). | H |

## 3.5 Retrieval and Re-Ranking

**Priority: H**

| ID | Requirement | Pri |
|---|---|---|
| FR-5.1 | The system shall perform hybrid retrieval fusing BM25 and vector search via RRF. | H |
| FR-5.2 | The system shall support multi-query expansion (LLM rephrasings + keyword variant). | M |
| FR-5.3 | The system shall de-duplicate near-identical query variants and candidate chunks. | M |
| FR-5.4 | The system shall re-rank candidates with a cross-encoder (`bge-reranker-v2-m3`). | H |
| FR-5.5 | The system shall normalise reranker scores and apply a relevance floor (`RAG_RELEVANCE_THRESHOLD`, default 0.3). | H |
| FR-5.6 | In Hierarchical mode, a matched child shall expand to its parent section for context. | H |
| FR-5.7 | The system shall de-duplicate results by parent, keeping the highest-scoring entry. | M |
| FR-5.8 | The system shall strip `[CONTEXT]` blocks from any text sent to the LLM. | H |
| FR-5.9 | The system shall return the top-K (default 3) grounded passages to the generator. | H |

# 4. External Interface Requirements

## 4.1 User Interfaces

- **Web UI (SvelteKit):** chat workspace, knowledge management, admin settings,
  model management, user/group administration.
- Responsive layout for desktop and tablet; light/dark themes.
- Admin → Settings → Documents exposes chunking strategy, chunk size/overlap,
  extraction engine, embedding model, reranker, and thresholds.
- Streaming chat responses with visible source citations.

## 4.2 Hardware Interfaces

- Optional GPU for embedding and cross-encoder reranking acceleration.
- Standard server networking for inter-service TCP (MySQL 3306, Weaviate 8080,
  Neo4j 7687, MongoDB 27017, Ollama 11434).

## 4.3 Software Interfaces

| Interface | Protocol | Purpose |
|---|---|---|
| MySQL | TCP / SQLAlchemy + PyMySQL | System-of-record persistence + migrations (Alembic) |
| Weaviate | HTTP/gRPC | Vector + BM25 indexing and hybrid search |
| Neo4j | Bolt | Knowledge-graph storage/queries |
| MongoDB | TCP | Q-matrix / AKU vocabulary (deferred tagging) |
| Ollama | HTTP | LLM inference, enrichment, keyword extraction |
| Extraction engines | Library / HTTP | Marker / Docling / PyPDF / Tika document parsing |

## 4.4 Communication Interfaces

- **HTTPS** for client–server traffic (production).
- **WebSocket / SSE** for streaming chat tokens and live updates.
- **REST/JSON** API surface exposed by FastAPI (OpenAPI documented).
- Webhooks for channel integrations.

# 5. Non-Functional Requirements

## 5.1 Performance

| ID | Requirement |
|---|---|
| NFR-1.1 | A typical NCERT chapter (~28k chars) shall ingest end-to-end in ≤ ~15 s (regex keywords). |
| NFR-1.2 | Embedding throughput shall be ≈ 10–17 ms/chunk on GPU. |
| NFR-1.3 | Interactive query retrieval (search + rerank of candidate pool) shall target sub-second before generation. |
| NFR-1.4 | First streamed token shall appear promptly after retrieval completes. |

## 5.2 Security

| ID | Requirement |
|---|---|
| NFR-2.1 | Passwords shall be stored hashed; tokens shall be signed and expiring. |
| NFR-2.2 | Access to knowledge, chats, and admin functions shall be RBAC-enforced. |
| NFR-2.3 | Security-relevant actions shall be captured by audit logging middleware. |
| NFR-2.4 | Database service accounts shall be least-privilege and host-scoped. |
| NFR-2.5 | Secrets (DB URL, keys) shall be sourced from environment/config, not code. |

## 5.3 Reliability and Availability

| ID | Requirement |
|---|---|
| NFR-3.1 | Ingestion enrichment shall retry with backoff and fall back to raw text on LLM failure. |
| NFR-3.2 | A failed pipeline checker shall abort ingestion without partial/corrupt indexing. |
| NFR-3.3 | Indexed chunk count shall equal produced chunk count (verified by IndexingChecker). |

## 5.4 Scalability

| ID | Requirement |
|---|---|
| NFR-4.1 | The vector store shall scale to millions of chunk vectors (Weaviate HNSW). |
| NFR-4.2 | Ingestion shall process documents concurrently within configured worker limits. |
| NFR-4.3 | Corpus growth shall not require schema changes for new documents. |

## 5.5 Maintainability

| ID | Requirement |
|---|---|
| NFR-5.1 | Chunking strategies shall be pluggable behind a single dispatch point. |
| NFR-5.2 | Configuration changes shall not require redeployment (PersistentConfig). |
| NFR-5.3 | Schema migrations shall be managed via Alembic. |

## 5.6 Usability

| ID | Requirement |
|---|---|
| NFR-6.1 | Admin configuration shall be achievable via UI without editing files. |
| NFR-6.2 | Answers shall display citations so learners can verify against source. |
| NFR-6.3 | The UI shall provide clear ingestion status and error feedback. |

## 5.7 Portability

| ID | Requirement |
|---|---|
| NFR-7.1 | The stack shall run on Windows and Linux hosts. |
| NFR-7.2 | Stateful services shall be containerisable (Docker Compose). |

# 6. Data Requirements

## 6.1 Primary Database (MySQL `futureverserag`) — Key Entities

| Domain | Tables (representative) |
|---|---|
| Identity & access | `user`, `auth`, `access_grant`, `group`, `group_member`, `api_key`, `oauth_session` |
| FutureVerse user mgmt | `ins_fv_user`, `ins_fv_user_group`, `ins_fv_user_group_security`, `ms_fv_user_type`, `ms_fv_security_option`, `tr_fv_login_history`, `tr_fv_login_token`, `tr_fv_otp` |
| Knowledge & content | `knowledge`, `knowledge_file`, `file`, `document`, `folder`, `note`, `memory` |
| Conversations | `chat`, `chat_message`, `chat_file`, `message`, `message_reaction`, `chatidtag` |
| Models & tooling | `model`, `prompt`, `prompt_history`, `tool`, `function`, `skill` |
| Collaboration | `channel`, `channel_member`, `channel_file`, `channel_webhook` |
| System | `config`, `feedback`, `tag`, `alembic_version` |

## 6.2 Vector Store (Weaviate) — Chunk Schema (representative)

`chunk_id`, `text` (embedded), `raw_text`, `parent_id`, `parent_text`,
`document_id`/`file_id`, `header_1/2`, `breadcrumb`, `position_in_section`,
`content_type`, `keywords`, `topics`, `has_context`, `vector(1024)`.
(Foundation mode adds the NCERT schema fields: `paragraph_sequence`,
`sentence_count`, `attribute_tags`, `cognitive_frame`, `chunk_context_note`, …)

## 6.3 Graph Store (Neo4j)

Concept nodes and relationships derived from the corpus to support
graph-augmented retrieval and topic navigation.

## 6.4 Document Store (MongoDB)

Q-matrix / AKU attribute vocabulary keyed by subject and topic cluster —
prerequisite input for the deferred attribute-tagging phase (§8.2).

## 6.5 Data Retention & Integrity

- Verbatim corpus text in Foundation mode must never be edited (citation
  fidelity).
- Re-ingestion overwrites a document's vector collection atomically.
- Deleting a document removes its chunks from the vector store.

# 7. System Architecture

## 7.1 Logical Tiers

```
┌───────────────────────────────────────────────────────────────┐
│  Client (Browser)  — SvelteKit UI, streaming chat, admin       │
└───────────────▲───────────────────────────────────────────────┘
                │ HTTPS / WebSocket (REST + SSE)
┌───────────────┴───────────────────────────────────────────────┐
│  Application (FastAPI)                                          │
│   • Auth / RBAC / Audit middleware                             │
│   • Chat & RAG orchestration                                   │
│   • Ingestion pipeline (agents + checkers)                     │
│   • Admin / config (PersistentConfig)                         │
└───┬───────────┬───────────┬───────────┬───────────┬────────────┘
    │           │           │           │           │
 ┌──▼──┐    ┌───▼────┐  ┌───▼────┐  ┌───▼────┐  ┌───▼─────┐
 │MySQL│    │Weaviate│  │ Neo4j  │  │MongoDB │  │ Ollama  │
 │ SoR │    │vectors │  │ graph  │  │Q-matrix│  │  LLMs   │
 └─────┘    └────────┘  └────────┘  └────────┘  └─────────┘
```

## 7.2 Ingestion Flow

`Upload → Extract → Chunk (strategy) → Keyword → [CONTEXT] enrich (Hierarchical)
→ Dedup → Embed (bge-1024) → Index (Weaviate) → Checker gates each stage`.

## 7.3 Retrieval Flow

`Query → (multi-query expand) → hybrid BM25+vector (RRF) → dedup → cross-encoder
rerank → threshold + parent expansion → top-K → LLM generation with citations`.

## 7.4 Configuration Model

Runtime configuration is read from the `config` table first (PersistentConfig),
falling back to `.env`. Changes made in the Admin UI persist to the DB and take
effect without redeployment.

# 8. Other Requirements

## 8.1 Compliance and Content Integrity

- Corpus usage shall respect NCERT/source licensing.
- Answers shall be grounded and attributable to source passages.

## 8.2 Deferred / Future Requirements

| ID | Requirement | Status |
|---|---|---|
| FUT-1 | LLM attribute tagging (Pass 1/2 → `attribute_tags`, `cognitive_frame`, `proposition_sentence_map`). | Built, not wired |
| FUT-2 | MongoDB Q-matrix integration to drive Pass 2 tagging. | Pending |
| FUT-3 | Attribute-state-aware retrieval (Foundation serving model). | Pending |
| FUT-4 | Graph-augmented retrieval blending Neo4j concepts with vector hits. | Planned |

## 8.3 Operational Notes (Environment)

- The application connects to MySQL over TCP; the DB service user must be granted
  for the connecting host. Prefer `127.0.0.1` for a co-located DB to avoid
  LAN-IP/hostname grant mismatches.
- Docker must be running before ingestion/retrieval so Weaviate is available.
- Ollama models must be pulled locally before first use.

## 8.4 Acceptance Criteria (v1 demo)

1. A learner can upload an NCERT chapter and receive grounded, cited answers.
2. Both chunking strategies are selectable and produce indexed chunks.
3. Foundation chunks are verbatim (no `[CONTEXT]`) and content-type-aware.
4. Hybrid retrieval + rerank returns relevant passages above threshold.
5. RBAC prevents unauthorized access to knowledge and admin functions.
6. Full document lifecycle (upload → index → delete → purge) works end-to-end.
